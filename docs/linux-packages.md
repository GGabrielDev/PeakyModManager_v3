# Linux x86_64 distribution

Build with `npm ci`, `npm run build`, then `PMM_RELEASE_REPOSITORY=OWNER/REPO npx electron-builder --config electron-builder.config.cjs --linux AppImage deb rpm --x64 --publish=never`. Set `PMM_PACKAGE_MAINTAINER` to the distributor's name and email; the default attributes the workflow repository owner. Install `rpm` before running `node scripts/package-artifacts.cjs` to inspect actual DEB/RPM metadata, require the artifact matrix and generate checksums/evidence and a pinned Arch PKGBUILD. The recipe's AppImage URL is for the exact version and selected release repository. Publish those exact assets together before using the recipe.

AppImage uses the app's updater only when build-selected authority exists. DEB/RPM use their package manager. The Arch wrapper sets `PMM_PACKAGE_MANAGED=1` and installs extracted resources under `/opt`; the app must not replace those resources. Native packages install a shared desktop/icon/executable identity. They do not intentionally select a new default URL handler or remove user mod/config directories. The Arch recipe derives its package, executable, desktop and icon names from the resolved `linux.executableName`, and its `/opt` directory from the builder product name. For coexistence, configure a distinct `appId`, `productName`, `linux.executableName`, native `packageName` values and protocol scheme together. Merely changing `appId` does not change builder executable resources.

Downloadable DEB/RPM are installers, not signed APT/DNF feeds. The PKGBUILD is not an AUR publication. No ARM/Flatpak support is added. Example lifecycle validation on disposable hosts: Debian `apt install ./PACKAGE.deb`, install the next version, `apt remove peakymodmanager-v3`; Fedora `dnf install ./PACKAGE.rpm`, upgrade, remove; Arch `makepkg -si`, build/install the next recipe, `pacman -R peakymodmanager-v3-bin`. Verify preserved user data and the chosen default handler at each step.

Artifact inspection and headless packaging do not prove interactive install/upgrade/uninstall, browser handling or games. Those checks and GNOME/KDE/X11/Wayland evidence remain required in application #13 before claiming support. Both artifact and release paths gate on `scripts/package-lifecycle.cjs`: disposable Debian, Fedora and Arch containers install a 0.0.0 fixture, upgrade to the current package, remove it, and check that user data, unrelated resources and the selected handler survive. `smoke-results/package-lifecycle.json` records container image IDs and per-platform diagnostics. The earlier package uses current executable contents under an older package version to exercise package-manager transitions; it does not prove application data migrations. Packaged application smoke coverage is tracked by #8. The automatic release workflow is owned by #12.

Native removal hooks distinguish RPM upgrade counts and dpkg upgrade actions from final removal. They unregister the actual `/opt/<product>/<executable>` alternatives target only on removal, preserving a replacement installation during upgrades. Lifecycle checks also reject dangling executable links after removal.

FPM omits nonempty application directories from RPM ownership metadata. On final removal the hook prunes only empty directories below the configured application directory, without following symlinks or deleting user-added files. Native packages declare `findutils` for that cleanup; lifecycle failures identify any remaining executable, desktop entry or directory.
