# CI, previews and stable promotion

Bootstrap: create `dev` from the reviewed current `main`, target feature/issue PRs at `dev`, and promote only the same repository's `dev` to `main`. The current repository has only `main`; activating this flow/rules is human issue #15. Stack these implementation PRs in dependency order before enabling publication. No workflow can block a direct push after it occurs: repository rules must prevent it.

Require **Required CI** and **Source branch policy** from GitHub Actions on both branches, require PRs, forbid force pushes/deletion and restrict direct main updates/bypasses. Use a trusted required workflow/ruleset where available so a feature PR cannot replace its own guard. Verify an intentionally failing check and a feature/fork PR to main cannot merge; verify a passing same-repository dev promotion can. Fork PRs run read-only validation; no pull_request_target execution or publication secrets are supplied.

`npm test`, lint, check-only formatting and type/build run on Linux and Windows. Linux packages are inspected and actual packaged smoke runs before the aggregate gate passes. Remote publication depends on that gate and only runs for pushes to dev/main. Manual artifact workflows are convenience builds, not the automatic gate; the old manually published release workflow is removed.

Each feature PR adds `changes/UNIQUE.json`: `{ "bump": "patch", "summary": "User-visible change", "issue": "https://github.com/OWNER/REPO/issues/NUMBER" }`. Pick major/minor/patch during review, not from squashed commit text. Stable planning finds the highest reachable stable semver tag, takes only new entries since that tag, and applies the highest bump (major resets minor/patch; minor resets patch). Previously released entries are immutable and are not repeated. For the first release, use committed package.json version as baseline and apply reviewed bumps. No generated commit is pushed to main.

Preview versions use the next stable version plus `-preview.REACHABLE_COMMIT_COUNT.SHORT_SHA`. They identify exact dev revisions and remain ordered for normal non-rewritten dev history. A completed preview is immutable; keep the newest 20 owned completed previews, preserving stable/foreign releases and the current preview. Install a preview build deliberately to opt into the preview channel. Stable clients use latest metadata and reject prereleases. Every Linux/Windows artifact and updater file is generated from one plan/revision; package manager formats keep package-owned updates.

Publication uploads the complete asset set to a draft, then marks it published only after validation/upload succeeds. An interrupted draft is recovered for the same revision. Completed release reruns verify immutable revision/assets and do not publish duplicates. `SHA256SUMS`, exact source revision and reviewed changelog accompany release assets. No successful release is exposed on failed checks/builds. Completed releases should never be repaired by mixing newer artifacts; correct source and publish a new version instead.

Set `PMM_RELEASE_REPOSITORY` as a repository variable for a dedicated release destination; otherwise this repository is used. For cross-repository publication configure `PMM_RELEASE_TOKEN` with write access to that selected destination. The client embeds only public source/channel configuration; never tokens. Confirm default workflow token write permission for publication. Human desktop/browser validation remains #13; release notes explicitly mark it pending.

Before enabling automatic publication, validate the source/feed and staged N→N+1 upgrade, Linux native lifecycle checks, startup/multiple-URL behavior and preview retention recovery. Those dependencies are tracked in #3/#4/#8/#2/#5. The included CI entry points are reviewable infrastructure, and are not evidence that all dependent runtime features already pass.
