# CI, previews and stable promotion

Bootstrap: create `dev` from the reviewed current `main`, target feature/issue PRs at `dev`, and promote only the same repository's `dev` to `main`. The current repository has only `main`; activating this flow/rules is human issue #15. Stack these implementation PRs in dependency order before enabling publication. No workflow can block a direct push after it occurs: repository rules must prevent it.

Require **Required CI** and **Trusted promotion source** from GitHub Actions on both branches, require PRs, forbid force pushes/deletion and restrict direct main updates/bypasses. Use a trusted required workflow/ruleset where available so a feature PR cannot replace its own guard. Verify an intentionally failing check and a feature/fork PR to main cannot merge; verify a passing same-repository dev promotion can. Fork PRs run read-only validation. A separate metadata-only `pull_request_target` policy uses the trusted target-branch workflow, never checks out or executes PR code, and has no token permissions. Publication secrets are never supplied to PR validation.

`npm test`, lint, check-only formatting and type/build run on Linux and Windows. Linux packages are inspected and actual packaged smoke runs before the aggregate gate passes. Pushes to `ci/**` also exercise validation before the workflow is integrated. Remote publication depends on that gate and only runs for pushes to dev/main. Manual artifact workflows are convenience builds, not the automatic gate; the old manually published release workflow is removed.

Each feature PR adds `changes/UNIQUE.json`: `{ "bump": "patch", "summary": "User-visible change", "issue": "https://github.com/OWNER/REPO/issues/NUMBER" }`. Pick major/minor/patch during review, not from squashed commit text. Stable planning reads completed stable releases from the selected publication repository, resolves their recorded source revisions, and takes only new entries since the highest stable version. Source-repository stable tags provide the bootstrap baseline; tag ancestry from dev is not required. It applies the highest bump (major resets minor/patch; minor resets patch). Previously released entries are immutable and are not repeated. For the first release, use committed package.json version as baseline and apply reviewed bumps. No generated commit is pushed to main.

Preview versions use the next stable version plus `-preview.REACHABLE_COMMIT_COUNT.SHORT_SHA`. They identify exact dev revisions and remain ordered for normal non-rewritten dev history. A dev synchronization with no unreleased entries produces a preview of the next patch, without weakening feature-PR change-entry requirements or permitting empty stable releases. A completed preview is immutable; keep the newest 20 owned completed previews and protect the current preview. An older completed-preview rerun may temporarily retain its release in addition to those 20; later publication can prune it once it is no longer active. Preserve stable, draft and foreign releases. Ownership requires the automation schema, source revision and matching source repository. Legacy releases without a source-repository marker are owned only when the publication destination is the source repository itself; they are never pruned in a dedicated destination. Install a preview build deliberately to opt into the preview channel. Stable clients use latest metadata and reject prereleases. Every Linux/Windows artifact and updater file is generated from one plan/revision; package manager formats keep package-owned updates.

Publication uploads the complete asset set to a draft, then marks it published only after validation/upload succeeds. An interrupted draft is recovered for the same revision. Planning first resolves an existing release for the exact source revision and channel, including recoverable drafts, before consulting newer stable history. New releases include `release-plan.json`; reruns reuse that plan and fail if its identity mismatches or its download fails. For legacy releases without this asset, reconstruct against stable versions preceding their recorded version and preserve the original tag and notes. Multiple existing identities for one revision/channel fail planning. Completed release reruns verify immutable revision/assets and retry preview retention without publishing duplicates. Release notes record source repository/revision, and `release-baseline.json` accompanies the assets so dedicated release repositories preserve the source baseline. Planning must have that source commit available from the full source-repository checkout; API errors fail planning rather than reverting to a stale version. `SHA256SUMS`, exact source revision and reviewed changelog accompany release assets. No successful release is exposed on failed checks/builds. Completed releases should never be repaired by mixing newer artifacts; correct source and publish a new version instead.

Set `PMM_RELEASE_REPOSITORY` as a repository variable for a dedicated release destination; otherwise this repository is used. For cross-repository publication configure `PMM_RELEASE_TOKEN` with write access to that selected destination. The client embeds only public source/channel configuration; never tokens. Confirm default workflow token write permission for publication. Human desktop/browser validation remains #13; release notes explicitly mark it pending.

Before enabling automatic publication, validate the source/feed and staged N→N+1 upgrade, Linux native lifecycle checks, startup/multiple-URL behavior and preview retention recovery. Those dependencies are tracked in #3/#4/#8/#2/#5. The included CI entry points are reviewable infrastructure, and are not evidence that all dependent runtime features already pass.
